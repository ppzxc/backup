# Exhaustive CLI Command Contract Matrix with Invariant-Based Container E2E

## Status

Accepted

## Context

The CLI must prove that every command and option performs the behavior its user-facing contract describes. Literal exhaustive testing of every string and path is impossible, while repeating every logical option combination against real S3, SFTP, database, systemd, and Cron effects would make the default suite slow, noisy, and difficult to diagnose. ADR-0010 separates non-destructive CLI contracts from external lifecycle effects, and ADR-0014 reserves real setup-to-recovery behavior for the Container E2E Matrix.

## Decision

The default `cargo test` suite will include an exhaustive CLI Command Contract matrix. It will enumerate every logical command/option combination and every defined Option Behavior Class through the real parser and dispatch path, using strict test adapters that reject unexpected calls, arguments, environment values, profile names, dry-run values, and call order. Container E2E will continue to verify real external effects through domain invariants and representative storage, database, systemd, and Cron scenarios rather than repeating every logical option combination.

## Consequences

- A command or option is not considered covered merely because the process exits successfully; its adapter calls, output streams, exit status, artifacts, masking, and permissions must match the contract.
- The production binary and strict test adapters share the same CLI Command Contract, while test-only adapters remain outside production wiring.
- The default test suite gains a larger deterministic matrix, but real external lifecycle execution remains bounded by the existing Container E2E Matrix.
- Changes to command options require updating the contract matrix and the relevant domain invariant scenario.
- Coverage completeness is enforced by a regular Rust test and the exit status of `cargo test`; GitHub CI is not required. Local commit or push hooks may run the same gate but are advisory because local hooks can be bypassed.
- The matrix is table-driven: option combinations are generated from declared axes, while expected adapter traces, output, exit status, and artifacts are maintained as independent contract data rather than derived from the production implementation.
- When the approved contract conflicts with current behavior, the contract wins: tests are added or updated to expose the mismatch first, then the implementation is changed while preserving the documented command and option names.
- The command contract exposes a structured outcome containing stdout data, stderr diagnostics, exit status, generated artifacts, and relevant external state changes. The binary shell translates that outcome to process behavior; tests assert the outcome at the command seam and verify the translation separately.
- Each contract case receives an explicit CLI Runtime Context for profiles path, language, logging, scheduler mode, and adapter selection. Production converts process environment into this context once; matrix tests do not mutate process-global environment variables and can run in parallel.
- The library owns the single authoritative CLI schema and shared dispatch path. The binary is a thin production composition shell, and coverage guards inspect the same schema used by production parsing.
- The global `--profiles <path>` is resolved once into the CLI Runtime Context and always overrides the default path. Empty, whitespace-only, missing, unreadable, or invalid configuration paths fail configuration-dependent commands before any external adapter call and never fall back to the default. Configuration-independent `version` and help paths do not read the configuration. `uninstall --purge` is confined to the selected configuration scope.
- The global `--log-file <path>` is an explicit logging target: it takes precedence over system logging fallback, enforces parent mode `700` and file mode `600`, and fails the command before external effects if creation, opening, or permission enforcement fails. Journald -> Syslog -> default file fallback is allowed only when no explicit log path is supplied; diagnostic logs remain separate from stdout data and secrets are masked.
- `setup --lang <ko|en>` accepts only the declared language values and fails invalid values instead of silently selecting English. An explicit value overrides `LC_ALL`/`LANG` detection; omission resolves `LC_ALL > LANG > en`. The selected language affects setup prompts and user-facing output for all setup actions, but never changes configuration meaning, profile identity, or external adapter arguments.
- `setup --non-interactive` without an action runs the full Setup Wizard without prompts; with `dependencies` or `backend-init` it remains valid and preserves those actions' execution contracts. A non-interactive stdin without the flag fails before configuration mutation, missing required inputs are never replaced with example values or default secrets, and any failure preserves the previous configuration and scheduler.
- `uninstall --purge` requires `--yes` and performs no deletion when confirmation is missing. Without `--yes`, a regular interactive uninstall prompts on a TTY, returns success without mutation when declined, and fails in a non-interactive environment; `--yes` skips the prompt and proceeds within the approved scope.
- Root and nested `--help`/`-h` are parser-only exits generated from the authoritative CLI schema. They return exit status `0`, write help to stdout, write parser errors to stderr, and perform no configuration read, scheduler/adapter/Restic/report action, or log-file creation; environment language is used unless an explicit `setup --lang` overrides it.
- Every matrix case has a stable identity derived from command, option values or behavior classes, and CLI Runtime Context. Failure diagnostics include that case ID, input classes, context, expected versus actual adapter trace, stdout/stderr, exit status, and artifact inventory. Adapter traces exact-match call order, program, arguments, environment, and result; artifact assertions cover existence, path, format, content invariants, and permissions. A coverage guard verifies that the generator consumed every axis of the authoritative CLI schema.
- `setup dependencies` checks `restic`, `rclone`, and `resticprofile` independently and attempts installation for every missing dependency. A dependency is reported as installed only after download, extraction, permissions, replacement, and execution verification succeed. The command aggregates all results and returns exit status `1` if any item fails; successful installations are not rolled back.
- `setup backend-init` attempts every declared Backup Profile and enabled Secondary in deterministic order. Any failure produces exit status `1` and identifies the failed profile/backend, while leaving the Unified Backup Configuration unchanged. Because external repository initialization is not safely reversible, already successful initializations are not rolled back; rerunning the command must be idempotent.
- The deterministic `setup backend-init` order is primary first, ordinary Backup Profiles in normalized lexicographic order, and enabled secondary last exactly once. A secondary entry appearing in the ordinary profile set is deduplicated. The command attempts every target, aggregates failures, and returns exit status `1` if any target fails.
- Standalone `database` validates the configured Database Stream before invoking an external adapter. Missing configuration, unresolved profile/backend, invalid database type or URL, and missing credentials fail with exit status `1` without an external call. A normal run performs exactly one dump and one Backup Profile repository execution; `--dry-run` performs structural validation only, emits no secret or connection URL, and performs no dump, restic, or repository mutation.
- `restore --storage` is strict: the default `primary` and explicit `secondary` each select exactly one Backend Adapter. Missing, disabled, or unresolvable selected storage fails without fallback to another storage; `latest` is resolved within the selected storage only. Snapshot and target validation must complete before invoking the restore adapter.
- `restore --snapshot` defaults to `latest`; non-default values are passed to native restic snapshot resolution as an ID or unambiguous prefix. Missing or ambiguous snapshots fail with the adapter error, while empty, whitespace-only, or leading/trailing-whitespace values are rejected before the adapter call and are never replaced by `latest`.
- `restore --target` rejects missing, empty, whitespace-only, existing regular-file, and symlink targets before the restore adapter. Existing directories, including empty directories, are valid; missing directories are delegated to the engine only when their existing writable parent permits creation. Relative paths are resolved from the current working directory, and `--force` never deletes or recreates the target.
- `schedule disable` is configuration-independent and idempotent. It removes only Backup CLI-owned systemd timer/service artifacts and Cron markers, succeeds with a warning when none exist, returns failure when cleanup fails, and never registers a replacement scheduler or touches unrelated scheduler entries.
- `schedule status` is configuration-independent and queries only the scheduler selected by the capability probe. Active, inactive, and no-scheduler states are successful status data; probe or selected-scheduler query failures return exit status `1` instead of being reported as inactive.
- `version` and built-in `--version` share one canonical version value, write it to stdout, and exit successfully without reading configuration or invoking scheduler, Backend Adapter, or Restic. Invalid `--profiles` does not affect them; an explicitly supplied `--log-file` still follows the global logging contract, while verbosity flags do not alter version data.
- `--quiet` and any `-v` count are mutually exclusive parser inputs and return exit status `2` before logging initialization or command dispatch. Valid verbosity counts are partitioned as `0`, `1`, `2`, and `3+`, mapping to `info`, `debug`, `trace`, and `trace`; explicit CLI verbosity outranks `BACKUP_LOG` and `RUST_LOG`.
- `doctor` runs every diagnostic check to completion and aggregates `Pass`, `Warn`, `Fail`, and `Unavailable` results instead of short-circuiting. It is read-only: it cannot modify configuration, repositories, or scheduler state. Findings are structured on stdout, execution details go to stderr with secrets masked, and any `Fail` or `Unavailable` produces exit status `1` while warnings alone produce `0`.
- Report artifacts are written to temporary files and committed with an atomic rename. An explicitly selected existing `--file` may be atomically replaced; automatically timestamped names never overwrite a collision and receive a collision-avoiding name. In an all-report partial failure, already committed artifacts remain valid and available, failure reports are written when possible, and truncated files are never exposed.
- `--profile` selectors share one Profile Resolver contract across `run`, `copy`/`sync`, and `status`: exact configured keys only, no trimming, case conversion, prefix matching, or fallback. Empty, whitespace-only, leading/trailing-whitespace, and unknown values fail before any adapter call; Unicode keys are valid when exact. Omitted values retain command-specific resolution (`run` all runnable, `copy`/`sync` default, `status` all active).
